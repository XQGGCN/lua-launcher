## REVIEW-062-01 / P2：并发恢复检查把普通忙碌误标为损坏

模块的同实例 active 锁在第二次 `inspectModToggleRecovery` 到来时原先抛出普通 Error。Core 的 `assertInstanceUsable` 会把所有非取消异常视为恢复失败，加入内存阻断集合并将实例置为 error。因此两次只读 `prepareModToggle` 同时执行，就能把没有任何 journal 的正常实例锁成需要人工恢复。

作者通过源码分析提出，并实际执行修复前回归：同时发起两次默认 prepare，最终 `snapshot().instances[0].status` 为 error，实例目录仍只有 game；断言预期 ready 出现红灯。这不是仅推测的竞态。

现模块抛出明确的 `ModToggleBusyError`（`MOD_TOGGLE_BUSY`）；Core 对此直接返回可重试的忙碌，不标损坏。并发请求允许一方明确失败，不要求共享信号或同时成功。修复后独立测试确认状态保持 ready、`launcher.json` 不变、没有 marker，稍后检查可成功。退出和实例 mutation generation 仍单独废弃旧确认。

## REVIEW-062-02 / P2：intent 同 inode 外部编辑可能被清理

原恢复记录清理仅核对 inode，外部原位修改仍可保留同一 inode，随后清理可能删掉这份被改过的 intent。问题由集成者提出，模块作者修复并新增回归；本记录作者没有运行此问题的旧版红灯。

现清理要求完整文件身份一致，并有界重读、核对预期字节和删除前身份。提交前记录被改会中止，保留原文件与记录；文件名已经提交后记录被改，则保留编辑并返回警告，不反向恢复文件名。作者独立阅读最终实现并重跑两项相关回归，包含在模块 30 项及合计 52 项中。不是作者独立提出或亲自外部编辑的 UI 场景。

## REVIEW-062-03 / P2：新检测到的恢复错误未及时发布给界面

集成者通过源码检查发现：prepare 中检查外部坏 marker 时，`assertInstanceUsable` 会在内存设置 error 并安全拦截后续操作，但原实现仅记录日志和抛错；没有保存或 state 事件时，renderer 仍可能显示 ready。后端安全门一直有效，问题在可操作状态迟报。

现设置阻断状态后同步发送 state 快照，不依赖 `launcher.json` 成功写入。作者随后指出 setModEnabled 的 RecoveryError catch 有同根因：save 失败时只记日志；该入口也改为先同步发送错误快照，再尝试保存。作者在现有双名/损坏 journal 和双 unlink / stateRename 失败回归中补充实际断言：新 marker 后 prepare 拒绝、两个入口的 state 事件均包含 error，磁盘 launcher.json 保持原字节；没有新增镜像测试，总数仍为 52。独立重跑通过。两个分支均由源码发现，未运行修复前红灯。

## 定向覆盖

- 生产默认 Core 在真实临时目录执行 `.jar → .jar.disabled → .jar`，保留字节与 registry/state；禁用不猜历史来源，恢复原名后重关联。无来源、坏登记也不创建或改写历史登记。
- 严格 selection 字段及固定路径；令牌 120 秒 TTL、全局 32 个上限、原子消费、过期回收、跨实例/重放拒绝，同名外部替换不能借旧令牌改名。
- 首个 await 前取得实例锁，安装模组/资源、设置、清单及启动受保护；等待账户凭据期间的 main 锁由源码复核，未执行真实账户请求。
- 设置 mutation 经过完整周期后，已签发及仍在准备中的令牌都失效；旧清单跨越整个改名周期后也不能发布。退出取消等待 worker 结算，晚到 prepare 不签发令牌，已提交操作胜过迟到取消。
- installMod 对手工禁用文件、新版本改名、legacy 裸登记、BBSMC 来源、required 依赖、双文件和大小写伙伴的保护通过；CDN 请求为零，文件/登记/state 不变，目录时间与内容证明未创建再删除 staging。
- 实际 commit 注入原名 unlink 和目标回滚 unlink 双失败，生成真实双硬链接及 journal；继续注入 `stateRename` 失败，Core 仍阻止安装、启动和实例设置写入，并保留文件与恢复资料。
- 重启明确 source-only / target-only 只清 journal；双名、损坏记录保持 error 和证据，不被普通安装重试掩盖。模块还覆盖目录祖先/符号链接、名称冲突、目录预算、外部原位修改、替换、取消和提交边界。

## 残余边界与发布状态

Node 路径接口仍有通常的 TOCTOU 边界；五秒预算是合作式检查，不能强行取消已进入内核的文件调用。不宣称抵御任意同用户恶意进程或任意断电下完整持久恢复。硬链接不受支持时明确失败，不降级为覆盖式 rename 或复制删除。

缺 intent、空 marker 或不明确记录保持阻断。成功改名后的清理失败可返回警告并留下记录；空 marker 仍需人工检查，不猜测安全。内存恢复安全门不会因一次普通重试解除，人工处理后应重启再检查；不要自动删除双文件或外部编辑。
